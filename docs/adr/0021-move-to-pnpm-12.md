# ADR-0021: Move to pnpm 12, with the lockfile regenerated in its own change
- Status: Accepted
- Date: 2026-10-31
- Deciders: Ryan

## Context
[ADR-1016](1016-pnpm-supply-chain-settings-stay-explicit.md) says a new pnpm *major* is
evaluated in a stance review before `packageManager` moves. pnpm 12.0.0 shipped 2026-08-26 (latest
12.16.1); cycle-in pins `pnpm@11.5.3` (2026-06-10). The 2026-10-31
[stance review](../reviews/2026-10-31-stance-review.md) did the evaluation, against the v12.0.0
release notes and a trial:

- Nothing in the release notes renames or removes a setting we use (`minimumReleaseAge`,
  `trustPolicy`, `blockExoticSubdeps`, `allowBuilds`, `onlyBuiltDependencies`,
  `strictDepBuilds`, `overrides`). The one change that could bite, that unrecognised
  `pnpm-workspace.yaml` settings now fail the install, didn't.
- On a throwaway export, outside the repo with scripts off (ADR-0012), pnpm 12.16.1 installed,
  and lint, all tests and the build passed.
- But a `--frozen-lockfile` install fails when only `packageManager` changes: in 12 the package
  manager is itself a lockfile entry (`packageManagerDependencies`), and the lockfile also drops
  its `settings:` block. So the move rewrites the lockfile.
- pnpm 12 ships as a native binary that the npm package fetches on first run, rather than as
  JavaScript.

Ryan asked for the move to be recorded.

## Decision
Move cycle-in to **pnpm 12** (the current 12.x when the change is made): `packageManager` to it,
`engines.pnpm` to `>=12`, and the lockfile regenerated by pnpm 12, all in **one change of its
own** that does nothing else. That way the lockfile diff can be read as a format change, and
any dependency that resolves differently stands out.

Before it merges, it must pass every gate the stance review's trial couldn't run: CI itself
(where `pnpm/action-setup` reads `packageManager`), `pnpm audit`, `pnpm audit signatures`, the
licence allowlist and the OSV scan of the new lockfile.

## Alternatives considered
- **Stay on 11.x** (latest 11.28.9). Workable for now, but 11 will leave support, and the
  move only gets bigger as the lockfile ages.
- **Let Renovate propose it.** Renovate regenerates lockfiles as part of its updates, but which
  pnpm it would run to do that for a major move is untested here. Either way, a major's lockfile
  rewrite deserves a change that was made and read on purpose, not one batched among routine
  updates.

## Consequences
- Contributors and CI need pnpm 12. `engines.pnpm >=12` says so, and `packageManager` lets
  Corepack and `pnpm/action-setup` pick it up.
- The supply-chain settings carry over unchanged. ADR-1016's "set explicitly" now also covers
  12's defaults.
- The native binary is fetched on first run, from where pnpm's npm package says. That's a
  download outside the lockfile's integrity hashes; the binary's own provenance is pnpm's to
  attest.
- Promotion condition: none beyond ADR-1016's (evaluate the next major, 13, in a stance review
  first).
